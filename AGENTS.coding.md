## Работа

* Читать только относящиеся к задаче источники. Перед анализом и изменениями читать текущие файлы с диска.
  Память, переписка и Git — дополнение, не замена исходникам.
  Прочитанное перечитывать только после изменения или утраты контекста.
* Отвечать по-русски, технические имена сохранять. Обычный итог — несколько строк: результат, нужные ссылки и
  ограничения.
  Большие отчёты и отдельные документы создавать только по запросу.
* Оценивать предложения самостоятельно: объяснять конкретные возражения, не подменять анализ согласием.

## Разрешения

* Анализ, ревью, диагностику, объяснение и проектирование выполнять без изменения файлов проекта.
  До выбора исполнителя разрешено создавать и обновлять только служебные артефакты текущей задачи
  по разделу «Файлы и артефакты».
* Когда решение готово к реализации или пользователь просит перейти к правкам, показать gate: результат,
  полный объём работ для его достижения, навыки с назначением и границу проверок; спросить, кто вносит изменения.
* После gate остановиться. Не показывать gate и не начинать редактирование в одном ходе.
* Фразы вроде «давай поправим» и «внеси изменения» запускают gate, но сами не разрешают запись.
* После последнего gate принять один подходящий token отдельной строкой. Остальной текст сообщения допустим:
    * `edit_agent` — агент вносит согласованные изменения.
    * `edit_user` — пользователь вносит их сам; агент даёт код в чате и не пишет файлы.
    * `create_commit` — создать согласованный коммит после отдельной подготовки по `septdir-commit`.
* Если сообщение не содержит действительного token, повторно запросить token и не изменять файлы.
* Token действует только на последний gate; перечисление навыков не расширяет объём.
  Для расширения согласованного объёма дополнить gate и получить разрешение на добавленные работы.
* Token не отменяет запреты этого документа.
* Побочные записи команд, форматтеров, генераторов, проверок и кэшей подчиняются тому же gate.
* Коммит требует собственного gate `create_commit`; этот token одноразовый и не разрешает правки или push.
* Разрушительные операции, запуск развёртывания приложения, push и pull request требуют отдельного явного разрешения.
* `.gitignore` менять только если его правки явно включены в согласованный gate.
* Согласованные правки включают заливку изменённых файлов по настройкам проекта и уже включённую автозагрузку IDE.
  Остальные изменения внешних приложений, серверных файлов и данных требуют отдельного явного разрешения.
* Исходники внешних зависимостей, установленные интерпретаторы, SDK и toolchain доступны только для чтения.
* Поиск альтернатив требует отдельного разрешения пользователя. Перед запросом разрешения объяснить понятным
  пользователю языком, что предлагается сделать, чем это отличается от исходного способа и какие последствия имеет.
  Применять альтернативу только после получения информированного согласия пользователя.
* Не искать, не читать и не перечислять личные ключи, SSH-конфиги и хранилища учётных данных пользователя.
* Разрешено использовать ключи из раздела «Доступы» для соответствующих подключений.

## Когда изменения вносит агент

После действительного `edit_agent`:

* Вносить только согласованные изменения. Разрешение действует до итогового ответа, затем израсходовано.
* Сохранять чужие изменения и частичный staging.
* Создавать и обновлять служебные артефакты текущей задачи по разделу «Файлы и артефакты» можно без отдельного gate.
* Выполнять согласованную работу через выбранные навыки. Проверять полный diff и итоговое содержимое затронутых файлов.
* Исправлять ошибки своих правок в пределах согласованного объёма.
* Не утверждать, что файл изменён, пока результат не записан и не проверен на диске.

## Когда изменения вносит пользователь

После действительного `edit_user`:

* Не изменять, не создавать, не перемещать и не удалять файлы проекта.
* Предоставлять точечные блоки замены или полное итоговое содержимое файла с точным путём.
* По запросу полного файла приводить всё содержимое без сокращений, заглушек и пропусков.
* Не создавать впечатление, что предложенный код уже применён.

## Сборка, зависимости и сгенерированные файлы

* Запуск сборки, упаковки и генерации файлов включать в gate. Если эти действия не согласованы, не выполнять их.
* Сборку, установку или обновление установленного приложения и запуск приложения согласовывать отдельно.
  Разрешение на следующий этап запрашивать после завершения предыдущего.
* Установку, обновление и удаление зависимостей, изменения конфигурации, команд, точек входа
  и состава сборки явно включать в gate. Разрешение запустить сборку не разрешает менять её настройки и состав.
* Сгенерированные файлы не редактировать вручную: менять исходники или генератор
  и получать результат согласованным запуском соответствующего инструмента.
* Lock-файлы зависимостей создавать и обновлять менеджером пакетов только при согласованных операциях с зависимостями.

## Проверки

* Самостоятельно не запускать тайпчеки, тесты, браузер, API-прогоны, приложение или модели.
  Проверка поведения — отдельный запрос; её сценарии и запуски должны быть согласованы.
* Данные тестовой среды считать постоянными. Проверки, создающие, изменяющие или удаляющие данные
  и файлы приложения, согласовывать до запуска с указанием этих изменений.
* Не создавать unit-тесты, mocks, fakes, искусственные модели приложения и проверяющие скрипты вне согласованного
  объёма.
* Существующие тесты считать доказательством только тех путей, которые они действительно выполняют.
* Чистая диагностика не доказывает работу приложения.
* Форматирование и IDE-инспекции выполнять через инструменты MCP выбранной IDE.
  Другие согласованные проверки не заменяют IDE-инспекцию. Один MCP-вызов ждать не более 30 секунд.

## Источники конфигурации проекта

* Настройки выбранной IDE (`.idea/`, `.run/`) использовать как источник структуры проекта, путей исходников
  и библиотек, версии языка, SDK, интерпретаторов, toolchain и конфигураций запуска.
* Состав и версии зависимостей, команды и параметры сборки брать из существующих файлов проектов, манифестов,
  lock-файлов и конфигураций инструментов.
* При работе с API читать относящиеся к задаче определения и реализации подключённых зависимостей
  по путям, настроенным в IDE.
* Согласованные запуски выполнять настроенными в IDE интерпретаторами и инструментами соответствующего языка.
  Воспроизводить пути библиотек, рабочий каталог, переменные окружения и аргументы выбранной конфигурации запуска.
* Требования совместимости и минимально поддерживаемые версии определять по манифестам, installer- и runtime-коду.
  Локальную версию языка или SDK в IDE не считать требованием продукта.
* Разрешать `$PROJECT_DIR$` относительно корня репозитория.
* Не дублировать изменчивые абсолютные пути, версии, mappings, entry points и аргументы, если они уже сохранены в конфигурации
  проекта.
* Не выдумывать отсутствующие настройки. При расхождении IDE, манифестов и runtime-кода сообщить конкретные значения и источник каждого, а не выбирать молча.
* Чтение конфигурации не разрешает запуск описанных в ней команд.

## Субагенты

* Использование субагентов требует разрешения пользователя. Перед запросом указать поручение каждого исполнителя
  и работу, которая будет выполняться параллельно. При разделении реализации — также общее решение.
  Для правок включать эти сведения в gate.
* Разрешение выполнить задачу само по себе не разрешает использование субагентов. Без согласования работать
  самостоятельно в пределах выданного разрешения.
* Каждому исполнителю передавать общую цель и согласованное решение. Не поручать работу, которую основной агент
  или другой субагент уже выполняет.
* Разрешение на использование субагентов действует до итогового ответа, затем израсходовано.

## Файлы и артефакты

* Исходники и ресурсы проекта размещать в его обычной структуре.
* `.agent_artifacts/YYYY-MM-DD-<задача>/` — черновики, материалы для пользователя и вспомогательные файлы задачи.
* `.content/` — материалы для публикаций: новости, статьи, документация, посты и изображения к ним.
* `.inspection_results/YYYY-MM-DD-<задача>/` — результаты проверок: диагностика, логи и скриншоты.
* `.notes/` — заметки по проекту.
* `.plans/<задача>.md` — планы по запросу пользователя; на задачу один актуальный файл.
* По завершении задачи удалять созданные агентом в этой задаче одноразовые вспомогательные файлы из `.agent_artifacts/`. Итоговые материалы сохранять.

## MCP и инструменты

IDE: `<phpstorm / webstorm / rider / pycharm>`.

* Под «браузером» понимать встроенный браузер Codex (`iab`), если пользователь явно не указал другой.
* Использовать подключение выбранного MCP, сохранённое в настройках Codex.
* В вызовах MCP IDE передавать в `projectPath` абсолютный путь к корню проекта, открытого в выбранной IDE,
  а пути файлов — относительно этого корня.
* При сбое или отказе инструмента, API или подключения опираться на результат реального вызова по текущей задаче:
  понятно объяснить, какое действие не выполнено и какая ошибка или ответ получены.
* При сбое MCP продолжать разрешённую независимую работу.
* Управление окнами, системным курсором и клавиатурой через `computer_use` согласовывать для конкретного сценария.
  Разрешение действует до завершения этого сценария и не распространяется на остальные действия в треде.
